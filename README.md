# CRAYON PLANET — متجر رقمي (المرحلتان 2 و3: المتجر + Chargily Pay)

مشروع Next.js + Supabase + Chargily Pay جاهز للنشر. لا بيانات وهمية، ولا
دفع وهمي: أي طلب لا يصبح Paid إلا بعد تحقق حقيقي من Chargily عبر Webhook.

## متغيرات البيئة (Environment Variables)
انظر `.env.example` للقائمة الكاملة مع الشرح. أضفها في Vercel → Settings →
Environment Variables، وليس في الكود أبدًا.

| المتغير | أين تحصل عليه | ملاحظة |
|---|---|---|
| `NEXT_PUBLIC_SUPABASE_URL` | Supabase → Settings → API | عام |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | Supabase → Settings → API | عام |
| `SUPABASE_SERVICE_ROLE_KEY` | Supabase → Settings → API | **سرّي — خادم فقط** |
| `NEXT_PUBLIC_SITE_URL` | رابط Vercel بعد أول نشر، ثم نطاقك لاحقًا | يجب أن يكون حقيقيًا وليس localhost |
| `CHARGILY_SECRET_KEY` | لوحة Chargily → API Keys (Test ثم Live) | **سرّي — خادم فقط** |
| `CHARGILY_MODE` | `test` أو `live` | غيّرها يدويًا عند الانتقال للإنتاج |
| `RESEND_API_KEY` | حساب Resend → API Keys | **سرّي — خادم فقط** |
| `RESEND_FROM_EMAIL` | بعد التحقق من نطاقك في Resend | مؤقتًا `onboarding@resend.dev` |

لا تُدخل أي مفتاح سرّي في هذه المحادثة أبدًا — ضعها مباشرة في Vercel.

## خطوات Supabase المتبقية
1. نفّذ `supabase/schema.sql` إن لم يكن منفَّذًا بعد (المرة الأولى فقط).
2. نفّذ `supabase/migration_002_stage3.sql` (إضافي بالكامل: عمود `featured`، جدول `webhook_events`).
3. نفّذ `supabase/migration_003_security.sql` (يزيل صلاحية الإدراج المباشر في `orders` من المتصفح، لأن إنشاء الطلبات أصبح حصريًا عبر `/api/orders` على الخادم الذي يعيد حساب السعر الحقيقي من قاعدة البيانات).
4. في **Authentication → URL Configuration**: اضبط Site URL على رابط موقعك الحقيقي (رابط Vercel، ثم `crayonplanetdz.com` لاحقًا)، وأضف نفس الرابط + `/admin/reset-password` إلى Redirect URLs — وإلا فشل رابط "نسيت كلمة المرور" أو أعاد التوجيه إلى localhost.
5. تأكد من وجود حسابك في جدول `admins` (كما في الخطوات السابقة).

## خطوات Vercel المتبقية
1. **لا تُنشئ مشروع Vercel جديدًا.** استخدم نفس المشروع القائم.
2. أضف/حدّث متغيرات البيئة أعلاه (خصوصًا `NEXT_PUBLIC_SITE_URL`, `CHARGILY_SECRET_KEY`, `CHARGILY_MODE`, `RESEND_API_KEY`).
3. ادفع هذا الكود (استبدال الملفات بنفس المسارات) وأعد النشر (Redeploy).

## Chargily Pay — ما يلزم منك أنت فقط
1. أنشئ حسابًا في https://pay.chargily.com (أو استخدم حسابك الحالي).
2. من لوحة التحكم، فعّل **Test Mode** وانسخ **Secret Key** الخاص بالاختبار → ضعه في `CHARGILY_SECRET_KEY` في Vercel، واضبط `CHARGILY_MODE=test`.
3. لا حاجة لتسجيل الـ Webhook يدويًا في أغلب حالات Chargily Pay V2 — يُرسل تلقائيًا إلى `webhook_endpoint` الذي يحدده كل طلب دفع (`/api/webhooks/chargily`)؛ إن طلبت لوحة Chargily تسجيل رابط Webhook ثابت، أدخل: `https://<رابط موقعك>/api/webhooks/chargily`.

## اختبار أول عملية شراء في Sandbox — خطوة بخطوة
1. أضف منتجًا حقيقيًا وانشره من `/admin/products`.
2. من المتجر، أضف المنتج للسلة واذهب إلى Checkout.
3. أدخل بريدك واسمك، واضغط "الدفع الآن". يجب أن يحوّلك الموقع فعليًا إلى صفحة دفع Chargily (بيئة Test).
4. استخدم بيانات بطاقة الاختبار التي توفرها Chargily في وضع Test (تجدها في توثيقهم أو لوحة تحكمك — لا تخترع رقم بطاقة).
5. أكمل الدفع التجريبي. يجب أن تعود إلى `/checkout/done?order=...` وتشاهد "جارٍ التحقق من الدفع…" ثم — خلال ثوانٍ — "تم الدفع بنجاح" بعد أن يصل الـ Webhook الحقيقي.
6. تحقق من `/admin/orders`: يجب أن تتحول حالة الطلب إلى `Paid` ثم `Delivered` تلقائيًا (فقط إذا كان `RESEND_API_KEY` مضبوطًا وأُرسل البريد فعليًا؛ غير ذلك تبقى الحالة `Paid` عمدًا لتنبيهك).
7. تحقق من بريدك: يجب أن يصلك رابط تحميل موقّع صالح 48 ساعة.
8. **اختبر أيضًا الفشل/الإلغاء**: ألغِ عملية الدفع من صفحة Chargily نفسها، وتأكد أن الطلب يتحول إلى `Failed` أو `Cancelled` ولا يصل أي بريد بملف.
9. **اختبر بريدًا غير صالح**: أدخل بريدًا بصيغة خاطئة في Checkout وتأكد أن النظام يرفضه قبل الوصول إلى Chargily.

## الانتقال إلى Live Mode (بعد نجاح كل اختبارات Sandbox)
1. في لوحة Chargily: فعّل حسابك للإنتاج (قد يتطلب توثيق هوية/نشاط تجاري من طرف Chargily).
2. انسخ **Live Secret Key** وضعه في `CHARGILY_SECRET_KEY` في Vercel، وغيّر `CHARGILY_MODE=live`.
3. تأكد أن `NEXT_PUBLIC_SITE_URL` يشير إلى نطاقك النهائي الحقيقي.
4. نفّذ عملية شراء حقيقية بمبلغ صغير من بطاقتك الخاصة للتأكد من وصول الأموال والبريد فعليًا قبل الإعلان عن الإطلاق.

## ما تم إنجازه في هذا الدور
- تدقيق شامل وإصلاح أخطاء Build حقيقية (`useSearchParams` بدون Suspense في 3 صفحات، نمط صور Supabase في `next.config.js`).
- تكامل Chargily Pay كامل بالمكتبة الرسمية: إنشاء جلسة دفع بمبلغ مُتحقَّق من الخادم، Webhook يتحقق من التوقيع (`verifySignature`) ويمنع التكرار (جدول `webhook_events`)، ولا يُحوَّل أي طلب إلى Paid إلا من هذا المسار فقط.
- **إصلاح ثغرة تلاعب حقيقية**: إنشاء الطلبات كان يتم مباشرة من المتصفح بسعر يُرسله العميل نفسه. أصبح الآن حصريًا عبر `/api/orders` الذي يعيد قراءة كل سعر من قاعدة البيانات، مع إزالة صلاحية RLS العامة المقابلة.
- روابط تحميل موقّعة ومؤقتة (48 ساعة) من bucket خاص، لا تُكشف أبدًا كرابط دائم.
- بريد إلكتروني عبر Resend (تأكيد الشراء، نجاح الدفع مع الرابط، فشل الدفع) — تم تصحيح استخدام معاملات المكتبة (`replyTo` بدل `reply_to`، فحص `{data,error}` بدل افتراض نجاح دائم).
- نسيت كلمة المرور / إعادة التعيين تعملان عبر Supabase Auth، وتستخدمان رابط الموقع الفعلي (`window.location.origin`) وليس localhost.
- استكمال لوحة الإدارة: العملاء، التقييمات (موافقة/حذف)، المشتركون، الكوبونات، خانة "منتج مميز".
- نموذج تقييمات على صفحة المنتج (يبقى غير منشور حتى تعتمده أنت من لوحة الإدارة)، منتجات مقترحة حقيقية فقط، نموذج اشتراك بريدي في الـ Footer يمنع التكرار عبر قيد `unique` على البريد.
- SEO: عنوان/وصف لكل صفحة، Open Graph، أيقونة الموقع (favicon/apple-icon من هويتكم)، `canonical` للصفحات الديناميكية.
- تدقيق أمني: لا سرّ واحد يصل إلى كود المتصفح (تحقّق آليًا)، كل استيراد نسبي في المشروع يشير إلى ملف موجود فعليًا (تحقّق آليًا)، فحص صياغة (syntax) لكل ملفات المشروع الـ49 دون أي خطأ.

## نتيجة npm run build — بصراحة تامة
**لم أستطع تنفيذ `npm install` ولا `npm run build` فعليًا في بيئة العمل هذه**، لأنها بلا اتصال إنترنت (محاولة `npm install` فشلت بخطأ 403 من الشبكة، كما هو متوقع من إعدادات هذه البيئة). لذلك لا أستطيع أن أؤكد لك نجاح `next build` الفعلي بنفسي، ولن أدّعي ذلك.
بدلًا من ذلك، نفّذت أقصى فحص ممكن بلا إنترنت:
- فحص صياغة (parse-level syntax check) لكل الـ 49 ملف JS/JSX في المشروع عبر محلّل TypeScript المتوفر محليًا — **صفر أخطاء صياغة**.
- تحقّق آلي أن كل استيراد نسبي (`from '../...'`) يشير فعليًا إلى ملف موجود — **لا مسارات مكسورة**.
- تحقّق آلي أن كل ملف يستخدم React Hooks يحمل `'use client'` — **لا نواقص**.
- تحقّق آلي أن لا ملف عميل (`'use client'`) يستورد وحدات تحمل مفاتيح سرّية (`supabaseServer`, `chargily`, `email`) — **لا تسريب**.
- تأكدت يدويًا من توافق كل استدعاء لمكتبتي `@chargily/chargily-pay` و`resend` مع التوثيق الرسمي الحالي لكل منهما (بما في ذلك تصحيح خطأ حقيقي وجدته في استخدام `resend`: المعامل الصحيح هو `replyTo` وليس `reply_to`).

**يجب عليك أنت تنفيذ `npm install && npm run build` فعليًا** (محليًا أو سيقوم Vercel بذلك تلقائيًا عند النشر) قبل اعتبار المشروع جاهزًا نهائيًا. إن ظهر أي خطأ فعلي عند ذلك (أمر وارد رغم الفحوصات أعلاه، لأنها لا تغني عن type-check أو bundling حقيقيين)، أرسل لي نص الخطأ وسأصلحه فورًا.

## ما لم يُختبر فعليًا (يحتاج بيانات منك)
- **لا عملية دفع Chargily واحدة تم اختبارها فعليًا** من هذه المحادثة — لا أملك مفتاح Sandbox ولا اتصالًا بالإنترنت لتجربته. الكود مبني بدقة حسب التوثيق الرسمي، لكن "جاهز للإنتاج" لا يتأكد إلا بعد أن تُجري أنت أول عملية Sandboxفعلية باتباع القسم أعلاه.
- إرسال بريد فعلي عبر Resend لم يُختبر (يحتاج `RESEND_API_KEY` حقيقيًا).
- اسم `event.type` بالضبط الذي يرسله Chargily لكل حالة (`checkout.paid`, `checkout.failed`, `checkout.canceled`/`checkout.expired`) مبني على توثيقهم العام؛ إن استخدمت لوحتهم مصطلحًا مختلفًا عند أول اختبار حقيقي، أخبرني بنص الحدث الذي وصل فعليًا في جدول `webhook_events` وسأصحح المطابقة فورًا.
